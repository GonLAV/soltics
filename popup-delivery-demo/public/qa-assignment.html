Part 1 — System Understanding & Risk-Based QA Strategy 25%

1. Explain the System

The system delivers a personalized popup to a customer's website visitor in real time, in response to their behaviour. It has four zones: the client browser, an API layer, a campaign engine, and three data stores.

Component responsibilities

  • Solitics SDK (client browser) — embedded on the customer's site. Calls SDK init once, opens a WebSocket, fires REST events for user actions (page_view, add_to_cart), and renders whatever popup instruction arrives on the socket. Reports popup_displayed / popup_closed back over REST.
  • API Layer — the REST surface (api.js). Validates and routes SDK init, event ingestion, and campaign CRUD. Every event ack contains the engine's decisions.
  • Event Ingestion — normalises incoming events, writes them to the Analytics store, and folds them into the user's profile (counters that drive segments).
  • Profile & Segmentation — derives segments from profile traits and counters (e.g. shoppers when cart value > 0, high_intent unless eligible:false, vip from a tier trait).
  • Campaign Manager / Audience & Rules / Decision Engine — the brain. For every event, loads active campaigns, filters by trigger event, checks audience-segment overlap and extra field conditions, then applies frequency caps. Every rejection carries a machine-readable reason.
  • Action Sender — on a positive decision, stamps a deliveryId and pushes the instruction down the user's WebSocket; if no socket is live yet, the instruction queues and flushes on connect.
  • Real-time Server — owns the WebSocket registry; one socket per session.
  • Data stores — Campaigns DB (definitions/status), User Profiles DB (traits, segments, delivery history), Analytics DB (raw event + delivery log).

Data flow

  1. SDK init (REST) → profile identified, session created.
  2. SDK opens the WebSocket for that session.
  3. User acts → SDK POSTs the event → Ingestion writes analytics and updates the profile → Decision Engine evaluates every active campaign → on a match, Action Sender pushes the instruction over the socket → SDK renders one popup → SDK reports popup_displayed/closed back over REST.

Synchronous vs. asynchronous

Synchronous: SDK init; POST /api/v1/events, whose 202 ack includes the full decision list per campaign.

Asynchronous: the popup push over the WebSocket is decoupled from the REST call that triggered it — the client learns "a campaign will fire" from the ack, but receives the render instruction on a separate channel, at a separate time, that can even queue if the socket isn't open yet.

Three highest-risk failure points

1
REST/WebSocket race at connect time

A decision can fire before the socket finishes its handshake. The queue is in-memory and single-process — a dropped reconnect or server restart silently loses the delivery, with nothing in the REST response to reveal it.

2
Shared mutable profile state under concurrency

Two events for the same user arriving close together read-modify-write the same in-memory profile; without atomic guarantees this can double-deliver past a cap or wrongly suppress a delivery.

3
Delivery idempotency at the Action Sender → SDK boundary

Network retries or re-sent WS frames can duplicate the same instruction. Correctness depends entirely on the SDK de-duplicating client-side — if that logic regresses, the symptom is a doubled popup in front of the customer's own customers.

Gates

Every Pull Request

Unit, integration, API tests, and the fast mock-only E2E specs (campaign-engine.spec.ts) — runs in ~1s.

Before every release

Full regression including the portable contract suite (popup-delivery.spec.ts) against staging, plus a performance smoke pass.

Continuously in production

Synthetic smoke checks (one delivery cycle every few minutes), dashboards/alerts on delivery rate, WS disconnect rate, and decision-engine skip reason distribution.

3. Release Prioritization

1
Decision Engine correctness (audience match, conditions, frequency caps)

Reduces the risk of the core business logic silently doing the wrong thing. A wrong decision is invisible anywhere except the customer's own screen.

2
WebSocket delivery path (queue-before-connect and de-duplication)

Reduces the risk of a correct decision never reaching the user, or reaching them twice. No HTTP status code catches this silent failure.

3
API ingestion and validation (event acceptance, session handling)

Reduces the risk of the front door breaking — a broken /api/v1/events endpoint takes down every campaign at once.

Part 2 — AI-Assisted Test Engineering 20%

1. Initial Prompt to an AI Coding Assistant

You are writing Playwright tests for popup delivery in a real-time campaign system.

System context:
- The SDK calls POST /api/v1/sdk/init, then opens a WebSocket at /ws?sessionId=...
- User actions are sent via POST /api/v1/events; the 202 response already contains
  the decision engine's per-campaign result, but the actual popup is pushed
  ASYNCHRONOUSLY over the WebSocket, separately from that REST ack.
- If the decision fires before the socket is open, the instruction queues and
  flushes on connect -- so delivery timing is not fixed or instant.
- The rendered popup must have data-testid="campaign-popup" and its close
  control data-testid="popup-close". Do not rely on CSS classes or #ids.
- Campaigns can be scoped to an audience segment (e.g. high_intent) and can be
  frequency-capped per user/session, so a user who already received a popup in
  this session must NOT be reused for a fresh delivery assertion.

Write tests for:
1. An eligible user (default profile) sees the popup with the exact copy
   "Special Offer" and can close it.
2. A non-eligible user (?testUser=non-eligible) sees no popup at all.
3. The same campaign instruction re-sent twice over the socket must still
   render exactly one popup (de-duplication).

Requirements:
- Use a fresh, unique userId per test so tests are safe to run in parallel.
- Use only web-first, auto-retrying assertions (expect(locator).toBeVisible(),
  .toHaveCount()) with an explicit timeout. Do NOT use waitForTimeout.
- Assert on content, not just visibility, and assert non-eligible users get
  toHaveCount(0) rather than assuming absence.
- Keep tests independent: no shared global state, no fixed ordering.
- Follow the existing repo style in tests/popup-delivery.spec.ts.

2. Review the AI Output

What likely caused the flakiness

  • Hard-coded sleeps instead of state-based waits — waitForTimeout(n) is either too short under load (flaky failure) or wastes seconds on every run.
  • Single, non-retrying isVisible() check racing the WebSocket push, instead of an auto-retrying expect(...).toBeVisible(timeout).
  • Reused user/session identity across tests, so frequency caps from an earlier test suppress delivery in a later one — reproduces intermittently only under parallel execution.
  • Assertions that check visibility but not content, so a stale/wrong popup still passes.
  • Selectors resolved against markup the AI guessed at rather than markup the app actually emits.

Improving the prompt and iterating

  • Give the model the actual contract — paste real endpoint shapes, data-testid attributes, and timeout budgets rather than letting it infer them.
  • Name the failure mode explicitly: "delivery is asynchronous relative to the REST ack; do not assume it has happened by the time the REST call returns."
  • Run the generated suite with --repeat-each=20 before trusting it — flakiness rarely shows on a single green run.
  • Feed the exact failure output back to the AI rather than re-describing the requirement.
  • Iterate in small diffs: fix one flakiness source, re-run 20x, only then move to the next.

Deciding a suite is production-ready

  • Zero failures across a repeated run (30-50x) both serially and with full parallelism.
  • No waitForTimeout left anywhere; every wait is tied to an observable state change.
  • Both the positive and negative path are asserted, not just the happy path.
  • The suite is order-independent — running one spec file alone gives the same result as running the whole suite.
  • A human who understands the delivery pipeline has read it and can explain why each wait and assertion exists.

Part 3 — Code Review 20%

The submitted test

test('Popup appears', async ({ page }) => {
    await page.goto('https://demo.site');
    await page.waitForTimeout(5000);
    const popup = page.locator('#popup');
    expect(await popup.isVisible()).toBeTruthy();
    await popup.locator('.close').click();
});

1. Highest-risk issues, prioritized

Reliability waitForTimeout(5000) is a fixed guess against an asynchronous, variable-latency delivery path. Fails under load, wastes 5s when delivery is instant.
Flakiness isVisible() is read once; wrapping in expect(...).toBeTruthy() throws away Playwright's auto-retry entirely.
No trigger The test goes straight to the URL and assumes a popup appears with no event fired and no way to know which user/session it is.
Missing assertions Visibility is checked, but not popup content, so a broken campaign with wrong copy still passes.
Fragile selectors #popup and .close are structural, not contract selectors; any markup refactor breaks the test.
No isolation A shared URL with no unique user id means frequency caps or prior runs can suppress delivery.
No negative case No verification the close actually closed it, and no non-eligible user test.

2. Rewrite

import { test, expect } from '@playwright/test';

test.describe('Popup delivery', () => {
  test('eligible user sees popup with correct content and can close it',
    async ({ page }) => {
      const userId = `qa-${test.info().testId}-${Date.now()}`;
      await page.goto(`/?userId=${userId}`);

      const popup = page.getByTestId('campaign-popup');

      // Delivery is async (REST decision -> WS push); wait on state, not time.
      await expect(popup).toBeVisible({ timeout: 10_000 });
      await expect(popup).toContainText('Special Offer');
      await expect(popup).toHaveCount(1); // catches accidental duplicate push

      await page.getByTestId('popup-close').click();
      await expect(popup).toBeHidden();
    }
  );

  test('non-eligible user sees no popup', async ({ page }) => {
    const userId = `qa-non-eligible-${Date.now()}`;
    await page.goto(`/?userId=${userId}&testUser=non-eligible`);

    await expect(page.getByTestId('campaign-popup'))
      .toHaveCount(0, { timeout: 5_000 });
  });
});

3. Explanation of improvements

  • Hard sleep replaced with auto-retrying, state-based assertions matched to the real async boundary.
  • Structural selectors replaced with contract-stable test ids.
  • Added content assertion and toHaveCount(1) — "technically visible but wrong or duplicated" now fails.
  • Added the negative path — a leak to a non-eligible user is the most business-critical assertion.
  • Per-test unique identity removes dependence on execution order and makes the suite parallel-safe.
  • Close is verified to actually hide the popup, not just that the click didn't throw.

4. AI Validation

  • Run the rewritten suite repeatedly (--repeat-each=30+) both serially and fully parallel to confirm zero flakiness.
  • Deliberately break the feature (disable the campaign, rename the test id) and confirm the test fails — a test that can't fail is worse than no test.
  • Confirm every locator and query param the AI assumed actually exists in the current markup/API.
  • Have a human who owns this feature review the assumptions block before merging.

Human Judgment

QA activities that always require meaningful human review

  • Interpreting acceptance criteria and deciding what NOT to test given limited time.
  • Any change to production alerting thresholds or on-call escalation rules.
  • Root-cause conclusions on a production incident.
  • The final release go/no-go decision.
  • Any test change that weakens or removes an existing assertion.

Where AI creates the greatest engineering risk

The main risk is false confidence: an AI-generated test that passes reliably but validates the wrong thing — a weak assertion, an over-mocked path, or a happy-path-only case dressed up as coverage. A subtler risk is AI "fixing" flakiness by loosening an assertion or adding a longer timeout instead of addressing the underlying race, trading a visible flaky test for an invisible false negative.

Decisions that should never be delegated completely

  • Whether a release is safe to ship.
  • The declared root cause of a production incident.
  • Whether a test's reduced strictness is an acceptable trade-off.

Preventing AI-generated defects from reaching production

  • Require at least one human-authored acceptance test per feature, independent of whatever AI drafted.
  • Hold AI-authored code and tests to the same review bar as human-authored — no fast lane.
  • Tag AI-assisted PRs so they can be sampled and audited specifically.
  • Keep a human-reviewed regression/contract suite as the final gate regardless of what produced the change underneath it.

Part 5 — Production Incident Investigation 15%

Yesterday afternoon, Marketing reported that popup delivery dropped from 98% to 67%. No deployments occurred, infrastructure is healthy, API latency is normal, no database alerts, only some customers affected.

Investigation (10 ordered steps)

1
Segment the drop first — is it concentrated by campaign, audience segment, browser, or customer site? Query the Analytics DB / decision-reason breakdown before forming a root-cause theory.
2
Read the decision engine's own reasons — every non-delivery carries a machine-readable reason (audience miss, condition failed, frequency cap). Look for one reason spiking among affected customers.
3
Check WebSocket health metrics — connection and reconnect rates, per region/customer. A correct decision still requires a live socket to reach the user.
4
Check for a runtime campaign or audience-rule change — campaigns can be edited via the API without a deploy, so "no deployments" doesn't rule out a config change. Diff current campaign state against a known-good point.
5
Check client-side health on affected sites — SDK console errors, ad blockers, CSP changes, or a broken script include, especially if the affected set clusters by browser or customer site.
6
Check whether the SDK asset itself changed (CDN-served solitics-sdk.js) independent of a backend deployment.
7
Look at latency at the tail (p99), not the average — "API latency is normal" may be an aggregate that hides degradation on a subset of high-traffic customers.
8
Plot the drop over time to see whether it is a step change or gradual decay, and correlate against any external event.
9
Reproduce against a known-affected segment/site with a synthetic test to confirm the leading hypothesis under controlled conditions.
10
Involve the right people — Marketing (confirm the figure is real), SDK/Frontend owners (client-side cause), Backend/Decision-Engine owners (rule or profile-state cause). Escalate immediately if evidence points to a shared decision-path bug affecting many customers.

Validation & Prevention

Confirm

Reproduce the failure deterministically for the identified segment, and confirm the timeline of the suspected cause lines up with when the drop actually started.

Validate the fix

Apply the fix on staging or a canary and re-run the previously-failing scenario repeatedly. Only after the metric recovers in production — real delivery rate back near baseline — is the incident closed.

Assess historical impact

Query the Analytics DB for the affected window to count how many eligible users did not receive a delivery, broken down by campaign, to give Marketing a concrete business-impact number.

Prevent recurrence

  • Add an alert on the specific failure signature found (e.g. a shift in the decision-reason distribution, or a guard on runtime campaign-rule edits).
  • Fold the reproduction case into the permanent regression and production-smoke suites so the same class of failure pages someone automatically before Marketing has to notice it.
