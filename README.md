# Solitics — QA Manager Home Assignment

A runnable demo of a real-time campaign delivery platform, plus the written
answers and the test suite that backs them.

## Run it

```bash
cd popup-delivery-demo
npm install
node server.js
```

Then open **http://localhost:3000**.

| URL | What it is |
|---|---|
| `/` | Mock customer storefront — the popup is delivered here. Demo controls sit bottom-left. |
| `/dashboard.html` | Live orchestration: every decision as it moves through the system |
| `/qa-assignment.html` | All five parts of the assignment |
| `/test-report/` | Playwright HTML report (generated by a test run) |

## Tests

```bash
cd popup-delivery-demo
npx playwright test                 # 27 tests, ~15s
```

Three suites, with different jobs:

- **`tests/campaign-engine.spec.ts`** — API-level. Pins the engine's decision
  *reasons*, not just outcomes, so a campaign that stops firing tells you which
  rule rejected it.
- **`tests/popup-delivery.spec.ts`** — the portable contract. Depends only on
  `data-testid="campaign-popup"`, `data-testid="popup-close"` and the campaign
  copy, so it runs against any environment:
  ```bash
  BASE_URL=https://staging.example.com npm run test:contract
  ```
- **`tests/demo-instrumentation.spec.ts`** — demo-specific instrumentation.

`tests-code-review/` is **deliberately separate and expected to fail**. It is
Part 3: the submitted test run verbatim against this app, paired with its
rewrite. A failing spec must never sit in the suite that gates a release.

```bash
npx playwright test --config=playwright.code-review.config.ts
```

## Architecture

One Node process. No framework, no database, one runtime dependency (`ws`).

```
Browser SDK ──REST──▶ API ──▶ Ingestion ──▶ Profile & Segmentation
     ▲                                              │
     └────WebSocket──── Real-time ◀── Campaign Engine
                                    (rules → decision → action sender)
```

Every decision carries a machine-readable reason code — `ELIGIBLE`,
`AUDIENCE_MISMATCH`, `CONDITION_FAILED`, `FREQUENCY_CAP`, `TRIGGER_MISMATCH`,
`INVALID_DEFINITION` — so a non-delivery is diagnosable without reading logs.

## Where this demo cuts corners

Stated plainly, because they are design choices for a demo rather than
oversights:

- **All state is in memory** (`src/db/index.js`). A restart loses profiles,
  sessions and runtime campaigns. Production: Mongo for profiles with an atomic
  `$inc` on frequency counters, Kafka partitioned by userId for events.
- **Single process.** The socket registry is a `Map`, so a decision made on one
  pod could not reach a socket held by another. Production: Redis pub/sub with
  a TTL'd `sessionId → podId` registry.
- **The frequency cap is per session**, and a page load mints a new session — so
  a refresh re-delivers. A welcome offer should be capped per user.
- **`popup_displayed` is trusted.** Feedback is accepted for delivery ids that
  were never issued, so attribution is forgeable.
- **The trace bus keeps 500 entries (~50 events) in RAM.** It is a
  visualisation, not observability; reason codes belong in a metrics counter.
